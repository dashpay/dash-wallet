# Platform SDK A: remove hidden legacy-client dependencies

**Planning baseline:** `feat/kotlin-sdk-phase-1` at `83a56f723` (2026-11-17, release 12.0.2).
**Tracker:** [dashpay/dash-wallet#1540](https://github.com/dashpay/dash-wallet/issues/1540).
**Scope:** preparatory step 2 of retiring the legacy `org.dashj.platform.sdk.platform.Platform` client. This document is a plan, not an implementation record.

## Goal and boundary

An SDK-backed read or a local identity-cache read should not construct the legacy `Platform` object just to obtain a contract ID, decode a stored identity, or record a valid identity ID. `PlatformServiceImplementation` currently appears lazy, but its constructor's `init` block dereferences `_platform?.client`. The pinned legacy `Platform` constructor calls `System.loadLibrary("sdklib")`, so injecting the service can load the old native library before any legacy operation is requested.

Keep a working legacy-client initializer. Transaction-metadata publish/fetch and DashConnect still call the legacy client, as do other legacy fallback paths. This step must preserve their behavior and does not claim that *every* application launch can avoid `libsdklib` yet. Removing old DPP model types is separate issue [#1541](https://github.com/dashpay/dash-wallet/issues/1541).

### Startup paths that still construct `Platform` after this step

Two ordinary-launch paths take the legacy client itself, not a value derived from it. They are out of scope here and bound what the cold-start check can claim:

| Path | Call sites | Why it stays |
|---|---|---|
| `BlockchainIdentity` takes a raw `Platform` | `IdentityRepository.kt:394` (inside `init()`); `RestoreIdentityWorker.kt:201`; `CreateIdentityService.kt:1755` | The legacy `BlockchainIdentity` constructor requires the client. Every wallet that has an identity therefore constructs `Platform` at startup until `BlockchainIdentity` is replaced or given a lazy client, which is a separate step under #1540. |
| Platform availability check | `MainViewModel.kt:553,573` via `PlatformService.isPlatformAvailable()` (`PlatformService.kt:227-245`) | It calls the legacy `platform.check()` three times on sync-stage changes and in a retry loop, for wallets without an identity too. The pinned SDK has no equivalent health call; choosing an SDK probe is an open decision, not part of this step. |

Because of the second row, any launch that opens the main screen on a Platform-supporting flavor still loads `libsdklib`. This step removes the constructions that happen merely because a service was injected or an SDK adapter ran; it does not yet make a normal launch legacy-free.

## Contract-ID source

The pinned Kotlin SDK exposes contract fetches, but no contract-ID accessor. Fetching by ID cannot supply the ID itself. Use a wallet-owned registry whose system IDs are copied from the canonical contract packages and verified against the currently pinned legacy definitions:

|---|---|---|
| DPNS | `GWRSAVFMjXx8HpQFaNJMqBV7MBgMK4br5UESsB4S31Ec` | `dashpay/platform/packages/dpns-contract/lib/systemIds.js` |
| DashPay | `Bwr4WHCPz5rFVAD87RqTs3izo4zpzwsEdKPWUT1NS1C7` | `dashpay/platform/packages/dashpay-contract/lib/systemIds.js` |

These three values also appear in the pinned legacy `SystemIds` class. The legacy `Platform` constructor registers `identity-verify` separately based on `NetworkParameters.id`: testnet `Bhptm3yBDhLkRNt7ofjpwaBHhMUKjDrQoPufKzQaxmpK`, Bintang `Fds5DDfXoLwpUZ71AAVYZP1uod8S7Ze2bR28JExBvZKR`, and production `EVKMFboB3QBUa9Jo7PP5bsLyohzUz8zvw5c2gJs1SfcX`. Check each supported flavor against the pinned definitions and a fetched SDK contract before changing an active read/write path. If unavailable, preserve the existing fail-closed/fallback result.

## Ordered implementation

1. **Introduce and validate the contract registry.** Switch all seven SDK adapter closures above and back `PlatformService.hasApp` with the registry. Keep the probe's legacy comparator and all legacy contract-cache operations. Confirm each adapter's flag-off, missing-ID, SDK failure, and legacy-fallback behavior.
2. **Defer the local identity decode.** Keep the loaded blob undecoded on the record and decode it, through the legacy client, on the first read of `identity`: once per record, thread-safe, and throwing to the reader on a corrupt blob. An unread, unassigned record saves its loaded hex unchanged; an assigned or read identity is serialized tolerantly as before. Cover no bounds, stripped contract-bound keys, concurrent reads, and a concurrent writer. `PlatformService.dpp` stays. Accepted behavior change: a corrupt blob used to fail every full load and now fails only where the identity is read, so loads that never read it (payments and profile observers, the restore error handler, recovery) proceed; `IdentityRepository.init` still fails closed for a registered identity.
3. **Move identity discovery and balances.** Use the SDK query APIs confirmed in the pinned `5.1.0-int36` artifact. Write and parity-test the identity JSON-to-legacy-`Identity` mapper first. Preserve retry spacing, cancellation, credit units, and the SDK-unavailable results given in the inventory. Route all five discovery callers through the shared implementation. As built: the lookup mirrors the legacy `fetch_identity_with_keyhash_sdk`, which falls back to the non-unique key-hash index (`fetchByNonUniquePublicKeyHash`: exactly one match is the identity, none is absent, two or more throws `SdkAmbiguousIdentityException` where the legacy lookup reported none) when the unique index has no identity. Discovery returns `null` only for a proved absence; every failure propagates (SDK `NetworkError`/`Timeout`, the 6 s per-round-trip bound, an unreadable wallet encryption key on an encrypted wallet, a native `LinkageError` as `SdkNativeLibraryUnavailableException`, start, proof and JSON failures), where the legacy read had returned `null` for network failures. The pre-cutover `preBlockDownload` catches a discovery failure and lets block download proceed instead of crashing its handler-less scope; the other callers report an error state or retry (spaced). A found identity is converted to the legacy model only after the legacy client exists (its key enums need `libsdklib`). Devnet (Sakura): the wallet gives the SDK no devnet quorum URL, so the SDK runtime cannot start there; identity discovery and balances need SDK devnet configuration and are unavailable on devnet until then (discovery throws, the repository balance is `null`, the `PlatformRepo` balance throws). There is no legacy route on devnet either.
4. **Move valid-ID bookkeeping.** Seed from the current identity, incoming-contact, and profile Room records; include newly encountered contact IDs and the two UI call sites. Replay once to a legacy client before its first query. Move the optional legacy identity cache write out of startup and into the same replay, keeping its CBOR failure behavior contained. Remove the public `stateRepository` accessor after the direct callers are gone. As built: the valid-ID calls and the startup cache write are deleted instead of replayed (see the two inventory rows), so there is no replay; `stateRepository` is gone from `PlatformService`.
5. **Make legacy initialization genuinely lazy and thread-safe.** Move the context-provider setup out of `PlatformServiceImplementation.init`; record quorum manager updates without constructing `Platform`; apply the latest manager when creation becomes necessary. `platformLazy` is unsynchronized today and the context provider reads a `lateinit` manager from a JNI callback thread; guard creation and the stored manager with one lock (or a synchronized lazy plus a `@Volatile` manager) so concurrent first callers get one client. Preserve the Sakura configured address provider. Keep the legacy initializer itself while callers remain. As built: one lock (`creationLock`) guards creating and publishing the client (double-checked over a `@Volatile` field) and storing and applying the manager; the context provider, the latest manager and the Sakura address handling are attached under it before the client is published. The JNI quorum callback reads the `@Volatile` manager without the lock and returns not-found while none is set, as before. A failing constructor publishes nothing and the next use retries. `platformLazy` is gone; the `profiles`, `contactRequests` and `identityVerify` wrappers and the `dpp`, `identities`, `names` and `client` accessors are synchronized `lazy` over the one client. The client factory and the platform-supported flag are constructor parameters of an internal constructor for tests; Hilt uses a secondary `@Inject` constructor with `createNetworkPlatform` and `Constants.SUPPORTS_PLATFORM`.

## Verification and acceptance

- **Parity:** registry values by flavor; SDK synthetic DPNS/profile/identity-verify documents; stored identity blob round-trips and byte-identical write-back of an unread record; first-key discovery for found, absent, and network-failure cases; exact credit balances; legacy proof verification.
- **Cold start:** fresh and restored wallets, with and without a Platform identity, unlocked and locked, foreground service and background application start, before and after committed L1 cutover. Count `Platform` construction and inspect loaded native libraries. Record which call first constructs it. The pass condition is that the first constructor is never service injection, an SDK adapter's contract-ID lookup, a load or observe of the identity record that does not read the identity, a `hasApp` guard, identity discovery, or a balance read. The two paths listed under "Startup paths that still construct `Platform`" are expected first constructors and are recorded, not failed. A background start that neither opens the main screen nor loads an identity must not construct `Platform` or load `libsdklib` at all; a path that actually uses the legacy client must initialize it exactly once.
- **Quorum/Sakura:** simultaneous first legacy callers, late masternode-manager delivery, SDK-sourced quorums while dashj is held, and Sakura HTTPS port preservation. A delayed client must still receive the correct manager and callback before any proved legacy query.
- **Build/grep gate:** assemble the affected wallet variants and run focused existing identity, SDK query, Platform sync, and quorum tests. Then grep for the seven `platformService.platform.apps` SDK-adapter lookups, any eager decode in `identityDataFrom`, direct UI `stateRepository` access, and any `stateRepository` call left in `initializeStateRepository()`; all should be gone. Legacy-only `Platform` uses remain expected.

## Parallel-work boundary

The transaction-metadata work owns `PlatformSyncService.kt`'s ticker (`:691-826`) and fetch/publish flows (`:1879-2598`). This plan touches startup `init()` (`:510-513`), contact bookkeeping (`:1234`), and `initializeStateRepository()` (`:3258-3275`). Develop against the same phase-1 tip, then rebase or merge and inspect the combined file diff. Do not remove the metadata ticker, the `SdkTxMetadataDecryptProbe` comparator, or its legacy fallback as part of this step.

DashConnect still calls `Platform.client` for identity, time, contract, key-budget, and protocol operations, and still registers a custom `Platform.apps` entry. Its migration can proceed separately. Until it and transaction metadata are migrated, preserve the legacy client initializer and do not declare #1540 complete solely because the hidden dependencies above are removed.
